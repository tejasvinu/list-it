# End-to-end audit — list-it

29 October 2026, at commit `3a1f5fc`. Scope: server code (auth, server actions, data loading, geo pipeline), configuration and deployment, build tooling, and a pass through every route in the browser at desktop and phone widths. The visual design review from 28 October is in [frontend-audit-2026-10-28.md](frontend-audit-2026-10-28.md) and isn't repeated here.

## Status

Same day, all findings except 15 (npm audit, upstream) are addressed in code; 13's route payload was left as is (about 100 points per ride is fine). Two parts of 8 need action in Atlas rather than code: give dev its own database user scoped to `list-it-dev`, and rotate the shared user's password. `npm test` now covers `lib/geo.ts` and ride validation.

## How it was checked

- Read every file in `lib/`, `app/` and the security-relevant components.
- `tsc --noEmit`, `eslint` and `next build` were run. All three are clean.
- `npm audit --omit=dev` was run (see finding 15).
- Fetched all 15 routes on the local dev server, both signed in and with no cookies, then checked status codes, payloads and what an anonymous visitor receives.
- Checked layout at 375 px across 10 pages.
- Ran the link → place → route → photos pipeline against the live services with 8 kinds of input.
- Fired 40 concurrent wrong PINs at a throwaway rider in `list-it-dev`. The rider was deleted afterwards.
- Checked the production response headers on list-it-2026.vercel.app.

## What's solid

- **Each page and action checks auth itself.** No page relies on the layout alone. Every page under `/g/[slug]` returns nothing without a viewer, and every action goes through `requireRider`. An anonymous request to the feed, a ride, the map or the activity page gets only the join screen. It gets no notes, comments or PIN data.
- **Ownership checks are right.** Only the owner can edit, delete, set status or refresh photos. Riders can delete only their own comments. A stop can be deleted by the rider who added it or by the ride's owner. Every lookup is scoped to the viewer's group.
- **Sessions are sound.** The cookie is httpOnly and HMAC-signed, with one cookie per crew. Bumping `sessionVersion` on a PIN change, PIN reset or removal signs out every other device.
- **The SSRF surface is small.** The server follows redirects only from `goo.gl` and `g.co`. Everything else is parsed, never fetched.
- **No secrets have ever been committed.** Only `.env.example` appears in git history. Dev and prod use different session and admin secrets.
- **The phone layout holds.** None of the 10 pages scrolls sideways at 375 px. Unknown crews, rides and riders all return 404.
- **Production is fast.** Server time on uncached production requests is about 90 ms. Slow requests from this machine were all in the TLS handshake.

## Findings

### High

#### 1. The PIN lockout can be bypassed with concurrent requests (verified)

[`verifyRiderPin`](../lib/auth.ts:47) reads `failedAttempts` from a rider document loaded before the check, then writes `fails + 1` back. Parallel guesses all see the same starting count. In the test, all 40 concurrent wrong PINs were checked. Afterwards the rider had `failedAttempts: 3` and was **not locked**.

A PIN has 4 digits, so there are only 10,000 possibilities. Anyone with the share link sees the roster on the join screen. Sending around 250 batches of 40 parallel `signIn` calls would try every PIN for a chosen rider. That takes minutes, not the roughly 14 days the lockout is meant to enforce.

**Fix:** reserve the attempt atomically before comparing. Use a `findOneAndUpdate({ _id, $or: [{ lockedUntil: null }, { lockedUntil: { $lte: now } }] }, { $inc: { failedAttempts: 1 } })` and refuse if nothing matched. Compare the PIN afterwards: reset the counter on success, or set `lockedUntil` once the returned count reaches 5. Consider a per-IP limit as well (see 11). Switch `scryptSync` to async `scrypt` while there: each guess currently blocks the event loop.

### Medium

#### 2. The admin login has no attempt limit

[`adminLogin`](../app/admin/actions.ts:17) sleeps 800 ms on a miss. That slows sequential guessing but not parallel guessing. The production `ADMIN_SECRET` is 16 characters, so the real risk depends on how random it is. Admin access reveals every crew's share link.

The admin cookie is a fixed value derived from the secret ([auth.ts:117](../lib/auth.ts:117)). It can't be revoked without rotating `ADMIN_SECRET`, and it lasts 30 days.

**Fix:** make sure the secret is long and random (32+ characters), and add a global failure counter in Mongo with a lockout. Optionally, put a random nonce in the admin cookie and store it so the cookie can be revoked.

#### 3. Ride data from the client is trusted, and malformed input causes 500s

[`validate`](../app/g/[slug]/actions.ts:201) checks types but takes the numbers on trust:

- `distanceKm`, `durationMin`, `route` (up to 1,500 points, every one sent to every feed), and unbounded `lat`/`lng`.
- `roadSplit` is stored as sent, so extra keys go into the database.
- A non-array `tags`, `seasons` or `photos`, or a `null` photo, makes `.map` or `.filter` throw. The caller gets an unhandled server error instead of the friendly "Something's off" message.

The risk is limited to crew members, but one bad request can make a ride wrong for everyone.

**Fix:** clamp `lat`/`lng` to India's bounds. Keep only the four `roadSplit` keys and require them to be finite and non-negative. Wrap array fields in `Array.isArray`. Ideally, re-run `routeFromHome` on save instead of trusting the preview's numbers. Alternatively, sign the preview on the server so it can't be altered.

#### 4. Links with a place name but no exact pin can resolve to the wrong place

When a Maps URL has no `!3d…!4d…` pin, [`resolvePlace`](../lib/geo.ts:265) geocodes the place text and ignores the `@lat,lng` viewport, which it uses only when there's no text. In testing, `…/maps/place/X/@12.1,77.1,13z` resolved to Electronic City, more than 80 km from the coordinates in the link. Search URLs (`/maps/search/…/@…`) and some desktop links have this shape.

**Fix:** use the viewport centre to bias the Photon query. Prefer the viewport if the geocoded result is more than a few tens of km away from it.

#### 5. "Plus codes work too", but a bare plus code is rejected

The landing page ([page.tsx:134](../app/page.tsx:134)) and the add-ride help text ([destination-form.tsx:551](../components/destination-form.tsx:551)) both say plus codes work. Pasting `Q4XQ+2C Kotagiri, Tamil Nadu` fails with "Paste a Google Maps link". Plus codes only work inside a Google Maps URL.

**Fix:** run `PLUS_CODE` on non-URL input in `resolvePlace` (the decoder already exists), or change both pieces of copy.

#### 6. Dates are a day off between midnight and 5:30 IST

[`todayYmd`](../lib/format.ts:44) uses the server's local time, which is UTC on Vercel. Saving a ride as "Ridden" without a date ([actions.ts:260](../app/g/[slug]/actions.ts:260)) records yesterday during those hours, which is exactly when riders leave at dawn.

[`daysUntil`](../lib/format.ts:36) also runs while the server renders [feed-view](../components/feed-view.tsx:73). In the same window, the server can count one day fewer than the browser does. That can change the "Up next" list and the "In N days" labels, causing a hydration mismatch.

**Fix:** compute the date in `Asia/Kolkata` on the server, for example with `Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Kolkata" })`. Compute "Up next" after mount, or pass the server's "today" down as a prop.

#### 7. The WhatsApp preview image is probably too large

The [OG image](../app/g/[slug]/d/[id]/opengraph-image.tsx) for a ride with a photo is a **717 KB PNG**. WhatsApp often drops images that large; the limit is commonly cited as about 300 KB. Image previews are the reason this route exists.

**Fix:** render without the background photo, or make it smaller or JPEG-like. Check the result with a real WhatsApp share.

#### 8. Dev and prod share a cluster, and the code defaults to the prod database name

`.env.local` points to the same Atlas cluster and user as production, and only `MONGODB_DB=list-it-dev` keeps them apart. Two things make that fragile:

- [`db.ts`](../lib/db.ts:146) and the scripts fall back to `"list-it"`, which is **production's** database name.
- A local `next build`/`next start` loads `.env.production.local` (the build log says so) and therefore talks to production.

A missing variable or a local production build writes to production data.

**Fix:** remove the default and throw if `MONGODB_DB` is unset. Give dev its own Atlas user with access to `list-it-dev` only. Consider keeping `.env.production.local` off this machine, since Vercel has the values.

### Low

#### 9. No security headers in production

Production sends only HSTS. There's no `Content-Security-Policy`/`frame-ancestors`, `Referrer-Policy` or `X-Content-Type-Options`. The crew slug is the secret, and it sits in the URL.

Browsers' default referrer policy sends only the origin to other sites, and SameSite cookies blunt clickjacking. So this is about defence in depth.

**Fix:** add `headers()` in [next.config.ts](../next.config.ts) with `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` (or `frame-ancestors 'none'`) and `nosniff`.

#### 10. "Open in Google Maps" can point anywhere

- The host check `/google\.|goo\.gl/` accepts `notgoogle.com` and `google.evil.example`, both verified.
- [`previewFromPlace`](../app/g/[slug]/actions.ts:153) passes a `mapsUrl` from the client straight through, and saving only requires `https://`.

**Fix:** match the host exactly (`google.com`, `google.co.in`, `maps.app.goo.gl`, `goo.gl`) and drop `mapsUrl` from `previewFromPlace`.

#### 11. Anyone with the link can lock any rider out

Five wrong guesses lock a named rider out for 10 minutes, and this can be repeated forever. That's the cost of a lockout per rider. A per-IP limit alongside it, and a slightly longer window for each repeat lockout, would make this less of an annoyance without weakening finding 1's fix.

#### 12. Rides from removed riders are orphaned

Only the owner can edit or delete a ride, and the admin pages have no ride tools. Once a rider is removed, their rides show as "Former rider" and nobody can change them.

#### 13. Performance will drop as crews grow

- Every cold start runs `ensureIndexes` and the "ridden" [`migrate`](../lib/db.ts:165) scan. Remove the migration once production has run it.
- `activity.deleteMany({ riderId, kind, destinationId })` runs on every reaction, "I'm in" and ridden toggle, and no index covers it.
- The [crew page](../app/g/[slug]/crew/page.tsx:13) builds the whole hydrated feed just to count rides per rider.
- The feed sends every route to the browser in full: 125 KB of HTML for 5 rides.

Nothing is slow today, but these grow with the number of rides.

#### 14. Free external services, observed failing during the audit

During the audit, Wikimedia Commons answered "too busy" twice, so the photo lookup returned nothing. Turning a link into a preview took 5–9 s for links and about 4 s for routing. OSRM's demo server, Photon, Nominatim and the OSM tile server have no SLA. OSRM and OSM tiles have usage policies against heavy use.

Routing already falls back to a straight-line estimate, and photos can be refreshed. Showing "Couldn't fetch photos, try again" would be better than showing nothing.

#### 15. `npm audit` reports 4 high-severity issues, none reachable

All four come from `zod` via `@vercel/functions` → `@vercel/oidc` → `@vercel/cli-config` (the CLI config parser), which user input never reaches. The suggested `--force` fix downgrades `@vercel/functions`. Wait for upstream instead.

#### 16. No automated tests

Lint, types and the build are the only checks. The pure functions in `lib/geo.ts` (link parsing, plus-code recovery, polyline decoding, road split) and `validate` would be cheap to cover. The bugs in 1, 3, 4 and 5 all sit in that code.

#### 17. Small touch targets on the feed

At 375 px, photo-credit links are 21 px tall and rider-name links are 19 px. The mobile nav labels are 11 px. These are below the 24 px minimum target size.

## Suggested order

1. Fix the PIN lockout (1). It's the only finding that exposes crew data to an outsider.
2. Guard the database name and split dev credentials (8), then add the admin limit (2).
3. Tighten `validate` (3) and the Maps host check (10). Both are small and in code that's already open.
4. Fix the IST date (6), plus codes (5), viewport bias (4) and OG image size (7). These are what riders will notice.
5. Add security headers (9) and a first set of tests (16) around `lib/geo.ts` and `validate`.
